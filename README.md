# Enclave Vaults

**A virtual HSM running inside a constellation of attested SGX enclaves.**

Enclave Vaults is Privasys's vHSM. Each vault is an Intel SGX enclave running [Enclave OS (Mini)](https://github.com/Privasys/enclave-os-mini) with the [`enclave-os-vault`](https://github.com/Privasys/enclave-os-mini/tree/main/crates/enclave-os-vault) module. Vaults hold **typed keys** and expose a typed HSM surface over RA-TLS: `CreateKey`, `ExportKey`, `DeleteKey`, `Wrap`, `Unwrap`, `Sign`, `Mac`, `UpdatePolicy`, `GetPolicy`, `GetKeyInfo`, `ListKeys`, `ReadAuditLog`, the pending-profile lifecycle for enclave upgrades, the threshold Ed25519 rounds (`FrostDkg*`, `FrostSign*`, `FrostAggregate`, `FrostReshare*`), `GetVaultIdentity` and `CanonicalisePolicy`. Vaults seal state to their own MRENCLAVE. By default the raw key material never crosses the enclave boundary: you ask the vault to sign or unwrap, and only the result leaves.

Multiple vault enclaves form a **constellation**. They are independent: each enforces the per-key `KeyPolicy` against the key or share it holds, with no cross-vault consensus and no shared trust. The [Enclave Vaults Client SDK](https://github.com/Privasys/enclave-vaults-client) does the discovery, the per-vault attestation, and the fan-out.

On top of the native surface, existing software can reach a vault-held key through the interfaces it already speaks: a [PKCS#11 3.1 module](https://github.com/Privasys/pkcs11-provider), a [KMIP 2.1 gateway](https://github.com/Privasys/kmip-gateway), and an Azure-shaped REST API + CLI.

Part of the [Privasys](https://privasys.org) Confidential Computing platform.

## Architecture

```
                 ┌──────────────────────────────────────┐
                 │  Vault directory                     │
  admin API ───► │  (the control plane)                 │ ◄── GET /api/v1/vaults

                 └───────────────────┬──────────────────┘      only: no keys, no shares,
                                     │ clients verify each      no policies, no approvals)
                                     │ vault's quote themselves
      ┌──────────────────────────┐   │
      │  Client SDK (Go / Rust)  │───┘
      │   directory client       │
      │   Client (Dial)          │──── mutual RA-TLS (one channel per vault) ───┐
      │   Constellation          │                                             │
      └──────────────────────────┘                                             ▼
   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
   │  Vault #1   │   │  Vault #2   │   │  Vault #3   │   │  Vault #N   │  ← SGX enclaves
   │  KeyObjects │   │  KeyObjects │   │  KeyObjects │   │  KeyObjects │   (enclave-os-mini
   │  + KeyPolicy│   │  + KeyPolicy│   │  + KeyPolicy│   │  + KeyPolicy│    + vault crate)
   │  + audit    │   │  + audit    │   │  + audit    │   │  + audit    │
   │  + sealed KV│   │  + sealed KV│   │  + sealed KV│   │  + sealed KV│  ← AES-256-GCM,
   └─────────────┘   └─────────────┘   └─────────────┘   └─────────────┘   MRENCLAVE-bound

   Each vault is independently authoritative for the keys it holds.
   The client SDK fans out across the constellation; vaults never talk to each other.
```

The directory is served by the control plane (constellations and their member vaults, exposed at `GET /api/v1/vaults`). It replaced the standalone Attested Registry that earlier versions shipped; the trust model is unchanged (the directory is an untrusted phonebook, see [Trust boundaries](#trust-boundaries)). The legacy `registry/` code is kept in this repo for reference only.

## What's a vault, exactly?

Each vault holds **typed keys**. The supported `KeyType`s are:

| Type             | Holds                                                     | Operations                          |
| ---------------- | --------------------------------------------------------- | ----------------------------------- |
| `RawShare`       | a Shamir share of an external secret                      | `ExportKey`, reconstructed client-side |
| `Aes256GcmKey`   | symmetric KEK / DEK                                       | `Wrap`, `Unwrap`                    |
| `P256SigningKey` | ECDSA P-256 signing key                                   | `Sign`                              |
| `HmacSha256Key`  | HMAC-SHA-256 key                                          | `Mac`                               |
| `FrostEd25519`   | one vault's share of a threshold Ed25519 key (FROST, RFC 9591) | threshold `Sign` (EdDSA), resharing; never exportable |

**Threshold Ed25519 keys.** A `FrostEd25519` key is generated by the vaults together (distributed key generation): no vault, and no client, ever holds the key. Any threshold of the vaults sign together, and the signature verifies under one ordinary Ed25519 public key. The client orchestrates every round; the vaults never call each other, and each vault checks the others' quotes over the round messages. A renewal reshares the key onto new vaults (or the same ones) under the same handle and public key, after the owner approves the exact target vaults and vault build in their wallet.

`exportable` is a key flag set at creation, **off by default**. A key created non-exportable can never be exported, even by its owner: every signature or unwrap happens inside the enclave.

`Sign` covers both a message the vault hashes (ECDSA-P256-SHA256) and a **pre-computed SHA-256 digest** the vault signs raw (`prehashed`), which is what TLS stacks and code signers need: the digest is signed once, never double-hashed. `Wrap` (AES-GCM) always generates the nonce in the enclave, so a nonce is never reused under a key.

Every key carries a `KeyPolicy` with these surfaces:

- `principals`: owner, managers, auditors (OIDC subjects or roles), and TEE principals named by attested measurement
- `operations`: per-op rules (`Sign`, `Wrap`, `ExportKey`, ...) gated by composable `Condition`s (`AttestationMatches`, `ManagerApproval`, `TimeWindow`, `OidcStepUp`). `OidcStepUp` is the owner's wallet approval: a passkey step-up through the IdP, bound to the exact operation, the vaults it is for, and the key's policy version
- `mutability`: which fields the owner can edit, which a manager can edit, which are `immutable` for the life of the key
- `lifecycle`: the key's lifetime (30 days by default, 90 days at most)

A new key's policy asks for the owner's wallet approval on promote, policy update and delete (and export, for an exportable key), unless it opts out explicitly with `"approval": "none"`.

**Expiry and renewal.** Every key expires. The app that uses a key renews it before expiry into its next generation (`<name>/gen-<n>`), in place or onto another constellation, carrying the key's own policy; the previous generation is then retired.

**Deletion.** A deleted key leaves a tombstone: its principals can still read the deletion and the audit log, and the handle stays reserved until the key's original expiry. A deleted name comes back only as a new key under `<name>/new-<k>`, with the owner's approval.

**Member ids.** Each vault has a member id, the hash of its own sealed key, returned with an attestation quote by `GetVaultIdentity`. Owner approvals name the member ids of the vaults they are for, so an approval for one constellation is refused by every other.

See [`docs/vault.md`](https://github.com/Privasys/enclave-os-mini/blob/main/docs/vault.md) in enclave-os-mini for the full schema and policy evaluator, and [`docs/vault-wire-formats.md`](https://github.com/Privasys/enclave-os-mini/blob/main/docs/vault-wire-formats.md) for the exact formats. [`docs/architecture.md`](docs/architecture.md) covers the deployment architecture.

## Standard interfaces

The RA-TLS wire protocol is the native surface. On top of it, the same in-enclave operations are reachable through the interfaces existing software already speaks. These are front-ends over the same policy engine, adding no new trust boundary, and a standard client can never weaken a key's policy:

- **PKCS#11 3.1**: [`Privasys/pkcs11-provider`](https://github.com/Privasys/pkcs11-provider) is a Cryptoki module that puts a vault-held key behind OpenSSL, Java (`SunPKCS11`), TLS servers, and code-signing tools with no change to the application. It can run a TLS server whose private key never leaves the enclave: every handshake signature happens in the hardware.
- **KMIP 2.1**: [`Privasys/kmip-gateway`](https://github.com/Privasys/kmip-gateway) lets enterprise key-management software use the constellation as a remote key manager, unchanged. The gateway itself runs as an attested confidential workload.
- **Azure-shaped REST + CLI**: a user creates a vault, holds keys in it, and operates them (sign / wrap / rotate) through the Privasys CLI (`privasys vault ...`) and a REST API. The API is a client-side proxy, so the data plane stays a direct, attested channel to the constellation; the platform mints the key-creation grant and never sees the material.

Standard clients get the baseline operations. Operations a key gates on an attested measurement or a fresh wallet approval go through the native API, which carries the richer policy; over the standard interfaces they fail closed.

## Enclave-upgrade lifecycle and measurement retirement

A key policy can name **attested measurements** (a `Tee` principal): a key answers only to specific enclave code. When a customer app's MRENCLAVE changes from `v(N)` to `v(N+1)`, the new measurement is added to the policy through a single primitive: `StagePendingProfile` puts it in a `pending` slot; `PromotePendingProfile` requires the owner's wallet approval, bound to the new measurement, before it merges into the policy's authorised set. The platform never auto-grants a new measurement access to customer key material: that is a protocol invariant, not a UX choice.

Promotion is **additive**: it authorises `v(N+1)` alongside `v(N)`, so a deploy can roll over or roll back cleanly. Retiring the old measurement is therefore a **separate, deliberate step** (`UpdatePolicy` removes a `Tee`): you first confirm `v(N+1)` actually holds the key (the running deployment is that proof). Tooling surfaces the authorised measurements and refuses to retire the current running one or the last remaining one, so an old version can be revoked while the key stays reachable.

## Trust boundaries

> The **directory** is a phonebook. `GET /api/v1/vaults` returns the active constellation's `(endpoint, measurement)` set and nothing else. It never sees keys, shares, policies, pending profiles, approvals, or audit data. Every other component treats it as untrusted.
>
> The **client SDK** does its own RA-TLS handshake and quote verification against each vault. All fan-out (Shamir distribution, threshold-key rounds, pending-profile staging / promotion / revocation, renewals, approval delivery) happens in the SDK.
>
> Each **vault** is a verifiable SGX enclave that enforces its own `KeyPolicy` against its own sealed state. There is no vault-wide policy and no cross-vault coordination. Trust comes from the attested enclave measurement.

A simpler way to say it: every component above the SGX enclave (directory, SDK, IdP) can be replaced by a third party without weakening the system. The vault enclave's MRENCLAVE is the only thing you ultimately trust.

## OIDC

Default IdP: **Privasys ID** (`https://privasys.id`, JWKS at `https://privasys.id/jwks`). A vault accepts bearers of one audience, set with `--oidc-audience` and sealed at first boot, so each constellation has exactly one: Privasys runs its production vaults on `privasys-platform` and its test platform's on `privasys-platform-test`, and the directory reports each constellation's audience (`oidc_audience`) for clients to request.

Each key's policy names its OIDC principals: a subject (`sub`), optionally with `required_roles`, or a role alone, which names everyone holding that role (for example an app's team). The owner approves governing operations with a passkey step-up in their wallet, which Privasys ID turns into a short-lived token bound to that one operation.

BYO IdP: set `oidc_issuer_url` on the vault binary and use `Principal::Oidc { issuer: "..." }` in `KeyPolicy.principals`.

## Vault enclave

The release is built by [`.github/workflows/vault.yml`](.github/workflows/vault.yml) from [`enclave-os-mini`](https://github.com/Privasys/enclave-os-mini) with `-DENABLE_VAULT=ON`, at the commit the workflow pins (overridable on a manual run). That build registers the egress, sealed KV store and vault modules only (no WASM runtime: a minimal TCB). [`vault/enclave`](vault/enclave/) is an example composition crate for a custom `ecall_run`; the release does not use it.

The build is **reproducible**: any fork of this repo can run `.github/workflows/vault.yml` (or its `docker run ...` equivalent locally) and recompute the same MRENCLAVE. Each tagged release (`vault-v*`) attaches `enclave.signed.so`, `enclave-os-host`, `mrenclave.txt`, and `build-manifest.json` (the exact `enclave-os-mini` ref + build image) to a GitHub Release, so the running enclave and the published artefacts share one measurement. See [vault/README.md](vault/README.md) for build details.

The **same SGX vault binary backs Shamir-distributed `RawShare` keys, threshold keys and full HSM-shaped keys.** Which behaviour you get is a property of the key type chosen at creation, not a different deployment.

## Quick start

```bash
# 1. Cut a signed release. vault.yml builds the enclave in enclave-os-mini's
#    reproducible build container and attaches enclave.signed.so + enclave-os-host
#    + mrenclave.txt + build-manifest.json to the GitHub Release.
git tag -s vault-v0.28.0 -m "vault-v0.28.0" && git push origin vault-v0.28.0

# 2. Run a vault on an SGX host (full runbook: docs/manual-sgx-deploy.md).
./enclave-os-host \
  --port 8443 --kv-path ./kvdata \
  --ca-cert ./ca-cert.pem --ca-key ./ca-key.pem \
  --egress-ca-bundle /etc/ssl/certs/ca-certificates.crt \
  --oidc-issuer https://privasys.id --oidc-audience privasys-platform \
  --attestation-servers https://as.privasys.org/verify \
  --attestation-token-file ./attestation-token.txt

# 3. Register the constellation in the platform directory (portal Admin → Vaults,
#    or the admin API) so clients discover it via GET /api/v1/vaults.

# 4. Talk to the constellation with the SDK.
#    https://github.com/Privasys/enclave-vaults-client
```
